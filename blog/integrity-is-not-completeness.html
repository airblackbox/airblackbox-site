Integrity Is Not Completeness

April 10, 2026 · Jason Shotwell · 9 min read

Every HMAC-SHA256 audit chain makes one promise: if a record is modified after it was written, the chain breaks and the verifier tells you. This is integrity. It is necessary. It is not sufficient.

The question that integrity does not answer:

How do you know a record wasn't silently deleted instead of modified?

If someone removes record #103 from the chain, records #102 and #104 still have valid hashes. The chain looks intact. The gap is invisible unless you knew record #103 existed in the first place. This is the completeness problem, and until today, air-trust did not address it.

air-trust v0.5.0 adds session-scoped completeness detection to the existing tamper-evident chain. New records get monotonic sequence numbers. The verifier checks for gaps. You now get two guarantees instead of one: records were not changed, and records were not dropped.

The Problem in Plain English

Imagine an AI agent that makes five tool calls in a session. Your audit chain records all five. Each record is HMAC-signed and chained to the previous one. If an auditor comes in and asks "was this log tampered with?", you can answer confidently: no, the chain is intact.

But what if the agent made six tool calls, and one of them — the one that accessed a customer database — was quietly removed from the chain before the auditor arrived? The remaining five records still verify. The chain is intact. The log is incomplete.

For EU AI Act Article 12, this matters. The regulation requires that high-risk AI systems maintain logs that "enable the monitoring of the operation of the high-risk AI system." Monitoring means you need to see everything. If an operator can delete inconvenient records without detection, the logging requirement is satisfied in letter but not in spirit.

How Session Completeness Works

The fix is deceptively simple. Every record in a session gets two new fields:

FieldTypeMeaning
session_seqintegerMonotonic counter starting at 0. Increments by 1 for each record.
prev_session_seqintegerThe session_seq of the previous record. -1 for the first record.

These fields are included in the HMAC payload, so they are tamper-evident just like every other field. If someone changes a sequence number, the chain hash breaks. If someone deletes a record, the gap between consecutive sequence numbers becomes visible.

A session also gets three lifecycle record types: session_start (must be the first record), checkpoint (optional waypoints), and session_end (should be the last record). A missing session_end means the session crashed or was interrupted — the verifier flags it.

What the Verifier Now Checks

The verifier performs two independent passes:

Pass 1: Integrity (unchanged). Replay the chain from genesis, recompute every HMAC. If any recomputed hash does not match the stored hash, the chain has been tampered with. This is the same check that shipped in v0.1.0.

Pass 2: Completeness (new). Group records by session_id. For each session, check that sequence numbers increase by exactly 1, that the first record is session_start, that the last record is session_end, and that there are no duplicates or rewinds.

The output is structured:

{
  "integrity": {
    "valid": true,
    "records": 47,
    "broken_at": null
  },
  "completeness": {
    "sessions_checked": 3,
    "sessions_complete": 2,
    "sessions_incomplete": 1,
    "issues": [
      {
        "session_id": "d4e5f6...",
        "issue": "gap",
        "expected_seq": 5,
        "actual_seq": 7,
        "record_index": 23
      }
    ]
  }
}

Integrity failures are FAIL (someone changed a record). Completeness issues are WARN (something is suspicious but the chain itself is intact). Missing session_end is INFO (could be a crash, not necessarily malicious).

Using It

Install or upgrade:

pip install air-trust==0.5.0

If you already use air_trust.session(), you get completeness for free. Every event written inside the session block now gets a session_id and sequence numbers automatically — including adapter events from wrapped LLM clients:

import air_trust

# Adapter events inherit the session_id automatically
with air_trust.session("my-pipeline") as s:
    client = s.trust(OpenAI())
    # This LLM call gets session_seq=1, prev_session_seq=0
    result = client.chat.completions.create(
        model="gpt-4o",
        messages=[{"role": "user", "content": "Hello"}]
    )
    s.log("Result validated")  # session_seq=2

Verify from Python:

result = air_trust.verify()
print(result["integrity"]["valid"])       # True
print(result["completeness"]["issues"])   # []

Or from the CLI:

# Human-readable output with PASS / WARN / FAIL tiers
python -m air_trust verify

# JSON output for CI/CD pipelines
python -m air_trust verify --json

What Completeness Does NOT Prove

This is as important as what it does prove. The SPEC.md v1.1 includes a threat model with explicit scope limits. Here they are:

  • Omission by the recording system. If the code never calls chain.write() for a particular action, there is no record to be missing. Completeness proves the chain is gap-free, not that the chain captured everything important.
  • Entire session suppression. If a session never starts (no session_start emitted), there is nothing to check. Completeness is scoped to sessions that exist.
  • Off-ledger activity. Actions taken outside the audited code path leave no trace. The chain can only witness what it participates in.
  • Cross-agent attestation. Agent A logging that it called Agent B does not prove Agent B agrees. That requires bilateral signatures, which is a separate problem (and a separate future spec).

The honest claim:

For sessions that were started and recorded, air-trust v0.5.0 can detect if records were dropped, duplicated, reordered, or if the session ended abnormally. It cannot prove that all sessions that should have existed do exist, or that all important actions were submitted to the chain.

This is a session-scoped completeness guarantee. It is meaningful for Article 12 because it proves the logging system itself is functioning correctly for the sessions it monitors. It is not a claim of universal coverage.

Backward Compatibility

v1.1 is additive-only:

  • Records from v0.4.0 (without session_seq) still verify for integrity. The completeness check simply skips them.
  • Mixed chains with both v1.0 and v1.1 records work fine.
  • No existing field meanings change.
  • The verify() output has the new integrity and completeness sections but also keeps the top-level valid, records, and broken_at keys for backward compatibility.

The Severity Table

IssueSeverityWhat it means

What Comes Next

Session completeness closes the single-agent gap. The next frontier is cross-agent attestation: when Agent A calls Agent B, can both sides prove the handoff happened? That requires bilateral signatures (Ed25519, not HMAC), a signed envelope protocol, and a way to correlate audit records across system boundaries.

We are not building that yet. The ROADMAP.md in the air-trust repo has the vision for signed handoffs and co-attestation, but we are explicitly waiting for real demand signal before committing engineering time. If cross-agent attestation is something you need, open a discussion on GitHub — that is exactly the pull signal that would move it from vision to build.
