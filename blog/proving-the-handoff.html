Proving the Handoff

April 10, 2026 · Jason Shotwell · 10 min read

Multi-agent workflows are now standard. Agent A researches. Agent B writes. Agent C reviews. Each agent publishes events to the audit chain, and the HMAC chain proves those events were not modified. But what the chain cannot prove is who sent what to whom, whether the handoff was acknowledged, or if the task itself was swapped in transit.

The core problem: HMAC uses a shared secret. Any party with the secret can sign. You need asymmetric signatures for cross-agent identity.

air-trust v0.6.0 adds Ed25519 signed handoff records to the existing HMAC-SHA256 chain. When Agent A hands off a task to Agent B, three new record types form a cryptographic proof: a request that Agent A signed, an acknowledgment that Agent B signed, and a result that Agent B signed. Together, they prove the handoff happened, both sides agreed on the payload, and the outcome is attributed to the right agent.

The Problem: Identity in a Shared Chain

Imagine Agent A (a researcher) is tasked with analyzing EU AI Act compliance trends and handing off findings to Agent B (a report writer). Agent A calls handoff_request(), publishing a record that says: "I am sending this research package to Agent B." The record is HMAC-signed and chained.

Later, an auditor asks: "Did Agent A actually send this? Could someone else have forged it?"

The answer, under the v0.5.0 chain, is: "Probably. We have HMAC, which proves the record wasn't modified after it was written. But HMAC doesn't prove who wrote it, because anyone with the key can sign."

This gap matters in multi-agent systems. When Agent A delegates work to Agent B, both agents need to leave a record that can be independently verified. Not just "a record exists," but "Agent A wrote this record, and Agent B received it and agreed on the payload."

For EU AI Act Article 12 (record-keeping for high-risk AI systems), this is critical. If multiple agents are operating the same system, regulators need to know which agent was responsible for each decision, which agent handed off to which, and whether all parties to a handoff agreed on what was being handed off.

The Design: Keeping HMAC, Adding Ed25519

The solution preserves the existing integrity model and layers asymmetric signatures on top.

HMAC-SHA256 remains unchanged. Every record, including handoff records, is chained via HMAC. If someone modifies a record after it is written, the hash breaks. The chain integrity check is identical to v0.5.0 and earlier.

Ed25519 is added for handoff identity. Ed25519 is an elliptic curve signature scheme. Each agent generates a keypair (private key for signing, public key for verification). When an agent writes a handoff record, it includes:

  • A SHA-256 hash of the payload (the task or result being handed off)
  • The agent's public key (so anyone can verify)
  • An Ed25519 signature over those fields (proving only the agent with the private key could have signed)
  • A nonce (replay protection)
  • The counterparty's fingerprint (who is on the other side of the handoff)

The HMAC still covers all of these new fields, so they are tamper-evident just like everything else in the chain.

The Handoff Protocol: Three Records

A complete handoff consists of three records, each signed by the responsible agent:

1. handoff_request (Agent A signs)

Agent A publishes:

  • type: "handoff_request"
  • interaction_id — A unique identifier linking all three records in this handoff (UUID)
  • counterparty_id — Agent B's fingerprint (so the record declares who is receiving this)
  • payload_hash — SHA-256(task_data). The hash of the work being handed off.
  • nonce — A random value (prevents replay attacks)
  • public_key — Agent A's Ed25519 public key
  • signature — Ed25519 signature of [interaction_id, counterparty_id, payload_hash, nonce]

2. handoff_ack (Agent B signs)

Agent B receives and processes the request. If the payload hash matches what Agent B received, Agent B publishes an acknowledgment:

  • type: "handoff_ack"
  • interaction_id — Same as the request (links them together)
  • counterparty_id — Agent A's fingerprint (Agent B acknowledges who sent this)
  • payload_hash — The same hash from the request. If they don't match, Agent B does NOT publish an ack.
  • nonce — Agent B's own nonce
  • public_key — Agent B's Ed25519 public key
  • signature — Ed25519 signature of [interaction_id, counterparty_id, payload_hash, nonce]

If the payload hash from the request does not match what Agent B received, the ack is not published, and a mismatch alert is logged. This proves the payload was not swapped.

3. handoff_result (Agent B signs)

After processing, Agent B publishes its output:

  • type: "handoff_result"
  • interaction_id — Same as request and ack (links all three records)
  • counterparty_id — Agent A's fingerprint
  • result_hash — SHA-256 of Agent B's output
  • nonce — Agent B's nonce
  • public_key — Agent B's Ed25519 public key
  • signature — Ed25519 signature of [interaction_id, counterparty_id, result_hash, nonce]

All three records are added to the chain in sequence. The verifier checks that all three are present, that signatures are valid, and that hashes match between request and ack.

What the Verifier Checks

The verification process has three passes:

Pass 1: Integrity (unchanged). Replay the HMAC chain from genesis. If any hash breaks, the chain was tampered with.

Pass 2: Completeness (from v0.5.0). Check for gaps in session sequence numbers within each session.

Pass 3: Handoff identity (new). For each handoff_request/ack/result triplet:

  • Verify the Ed25519 signature on each record using the declared public key
  • Confirm all three records are present (request + ack + result)
  • Confirm the interaction_id is the same on all three
  • Confirm the counterparty_id in request matches the public_key fingerprint in ack (and vice versa)
  • Confirm the payload_hash in request matches the payload_hash in ack
  • Confirm each nonce is unique (no replay)

The verifier output is structured:

{
  "integrity": {
    "valid": true,
    "records": 52
  },
  "completeness": {
    "sessions_checked": 3,
    "sessions_complete": 3
  },
  "handoffs": {
    "handoffs_checked": 2,
    "handoffs_valid": 2,
    "issues": []
  }
}

The severity levels are clear:

IssueSeverityWhat it means
Signature invalidFAILEd25519 signature does not verify. Identity is forged.
Missing handoff_ackWARNRequest sent but no ack. Did Agent B receive it?
Payload mismatchWARNRequest and ack disagree on payload_hash. Payload was swapped.
Counterparty mismatchWARNRequest says it goes to Agent B, but ack is from Agent C. Routing error or forgery.
Duplicate nonceWARNTwo records from the same agent use the same nonce. Possible replay.

Code Example: The Handoff Protocol

Here is how it works in practice:

from air_trust.events import Event, AgentIdentity
from air_trust.chain import AuditChain
from air_trust.keys import generate_keypair, compute_payload_hash, generate_nonce

# Create identities and generate keypairs
agent_a = AgentIdentity(agent_name="researcher", owner="jason@airblackbox.ai")
agent_b = AgentIdentity(agent_name="writer", owner="jason@airblackbox.ai")
generate_keypair(agent_a.fingerprint)
generate_keypair(agent_b.fingerprint)

chain = AuditChain()
iid = "handoff-001-2026-04-10"
task_data = "research EU AI Act trends in 2026"
task_hash = compute_payload_hash(task_data)

# Agent A sends handoff request
chain.write(Event(
    type="handoff_request",
    framework="raw_python",
    identity=agent_a,
    interaction_id=iid,
    counterparty_id=agent_b.fingerprint,
    payload_hash=task_hash,
    nonce=generate_nonce(),
))

# Agent B receives and verifies payload matches
received_hash = compute_payload_hash("research EU AI Act trends in 2026")
assert received_hash == task_hash, "Payload mismatch!"

# Agent B acknowledges
chain.write(Event(
    type="handoff_ack",
    framework="raw_python",
    identity=agent_b,
    interaction_id=iid,
    counterparty_id=agent_a.fingerprint,
    payload_hash=task_hash,
    nonce=generate_nonce(),
))

# Agent B does the work and publishes result
result_data = "EU AI Act Articles 9-15 now require..."
result_hash = compute_payload_hash(result_data)

chain.write(Event(
    type="handoff_result",
    framework="raw_python",
    identity=agent_b,
    interaction_id=iid,
    counterparty_id=agent_a.fingerprint,
    result_hash=result_hash,
    nonce=generate_nonce(),
))

# Verify the chain
result = air_trust.verify()
print(result["handoffs"]["handoffs_valid"])  # 1

CLI Verification

From the command line:

# Human-readable output
python3 -m air_trust verify

# JSON output for CI/CD
python3 -m air_trust verify --json

What Signed Handoffs Do NOT Prove

This is as important as what they do prove. The SPEC.md v1.2 includes a comprehensive threat model. Here are the explicit limits:

  • Key compromise. If Agent A's private key is stolen, an attacker can forge valid signatures that are indistinguishable from legitimate ones. Signed handoffs assume the keys themselves remain secure. If you suspect a key has been compromised, you must revoke it (future work: key rotation and revocation lists).
  • Collusion. If Agent A and Agent B cooperate, they can forge a fake handoff exchange that never actually happened. Both agents have keys and can create signatures that match. Identity verification works only if the agents are not collaborating.
  • Off-chain handoffs. If Agent A and Agent B communicate outside the audit chain (email, Slack, phone call), there is no record. The chain only witnesses exchanges that go through handoff_request() / handoff_ack().
  • Payload quality. The payload_hash proves the payload was not tampered with. It does not prove the payload is correct, useful, or safe. Hash matching is a necessary but not sufficient condition for trust.
  • Authorization. Ed25519 proves identity: "This agent signed this record." It does not prove authorization: "This agent was allowed to do this." For authorization, you need separate access control logic.

The honest claim:

For handoffs that flow through the chain, v0.6.0 can cryptographically prove which agent sent the request, which agent acknowledged it, whether both sides agreed on the payload, and which agent published the result. It cannot prove the keys were never compromised, the agents were not colluding, or that the payload itself is correct.

Backward Compatibility

v0.6.0 is fully backward compatible with v0.5.0 and earlier:

  • The HMAC chain is unchanged. v0.5.0 records still verify.
  • Session completeness checks still work on v1.1 records.
  • Handoff records are optional. They only appear when agents explicitly use the handoff API. Ordinary event records do not include Ed25519 fields.
  • Mixed chains (integrity + completeness + handoffs) all verify together.
  • No breaking changes to the Event model.

The only new dependency is the cryptography library, which is optional. Install with:

pip install air-trust[handoffs]

This brings in PyCA/cryptography for Ed25519 support.

What Comes Next

v1.2 is unilateral signing. Agent A signs "I am sending this" and "Here is my result." Agent B signs "I received it" and "Here is what I did."

Future work (v1.3) would add bilateral co-attestation: both agents sign a single joint handoff record, proving they both witnessed the exchange and agreed on the terms. This would close the collusion gap, though it requires both agents to be online and cooperating at the moment of handoff.

We are not building co-attestation yet. Real demand drives prioritization. If multi-party signatures are something you need, open a discussion on GitHub — that signal influences the roadmap.

Getting Started

Install the new version:

pip install air-trust==0.6.0

Generate keypairs for your agents (one-time setup):

from air_trust.keys import generate_keypair
generate_keypair("researcher-001")  # Creates ~/.air-trust/keys/researcher-001.private_key

Then use the handoff API in your agent code:

from air_trust.handoffs import handoff_request, handoff_ack, handoff_result

# Agent A
handoff_request(
    interaction_id="task-123",
    counterparty=agent_b,
    payload=research_findings
)

# Agent B
handoff_ack(interaction_id="task-123", payload=research_findings)
# ... do work ...
handoff_result(interaction_id="task-123", result=report)

Verify:

python3 -m air_trust verify --json

Get air-trust v0.6.0 with signed handoffs

pip install air-trust[handoffs]==0.6.0
