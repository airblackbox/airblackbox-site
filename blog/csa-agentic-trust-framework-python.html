CSA Agentic Trust Framework for Python AI Agents

April 9, 2026 · Jason Shotwell · 11 min read

The Cloud Security Alliance Agentic Trust Framework (ATF) is the first industry standard that asks a question regulators keep dodging: how do you know an AI agent is who it says it is? Version 0.9.1 of the public review draft landed earlier this year and is already being referenced in enterprise procurement checklists. We shipped native ATF conformance support in air-trust v0.4.0 this week. This post walks through what the framework is, what it asks of Python agents, and how to prove conformance with a single function call.

What the CSA Agentic Trust Framework Actually Is

The ATF is a specification for identifying, trusting, and progressively promoting autonomous AI agents. It answers three questions that the EU AI Act leaves open: who is the agent, what is it allowed to do, and how much autonomy has it earned? The framework sits underneath compliance regimes like the EU AI Act and ISO 42001 — it does not replace them. It tells you how to identify and promote individual agents so that the broader compliance machinery has something durable to attach to.

There are two structural pieces you need to understand before you can write any code:

  • Identity Core Elements. Five requirements, labeled I-1 through I-5, that describe the minimum identity surface every agent must expose.
  • Maturity levels. Four progressive tiers — Intern, Junior, Senior, Principal — that gate how much autonomy an agent is trusted with. Each level raises the bar on which core elements are MUST, SHOULD, or MAY.

An agent starts at intern, proves itself against a narrow set of MUSTs, and graduates upward. The maturity ladder is the framework's most interesting idea — it borrows directly from how human organizations grant autonomy to junior employees.

The Five Identity Core Elements (I-1 to I-5)

These are the five things every agent needs to expose before it can claim any ATF level. The air-trust implementation maps them directly to fields on the existing AgentIdentity dataclass we use for Article 14 identity binding in audit chains.

IDRequirementWhat it means in Python
I-1Unique IdentifierA persistent URN — e.g. urn:agent:air-blackbox:search-bot:1.2.0
I-2Credential BindingSHA-256 fingerprint over name:owner:version
I-3Ownership ChainA human owner and optional organization
I-4Purpose DeclarationA short string describing what the agent is for
I-5Capability ManifestA list of actions the agent is allowed to take

Notice that I-4 and I-5 are new — the other three already existed in air-trust 0.3.0 to support EU AI Act Article 14 identity binding. Adding purpose and capabilities took about twenty lines of dataclass code and zero new dependencies. This is the cheapest compliance upgrade you will ever ship.

The Four Maturity Levels

The ATF maturity ladder is where things get interesting. Each level raises the bar on which of the five core elements you have to satisfy.

LevelDescriptionMUSTSHOULD
InternSupervised, narrow task scopeI-1, I-3, I-4I-2, I-5
JuniorLimited autonomy, human-in-the-loopI-1, I-2, I-3, I-4I-5
SeniorFull core element set, broader scopeI-1, I-2, I-3, I-4, I-5—
PrincipalStrict: every core element is mandatoryI-1, I-2, I-3, I-4, I-5—

The promotion logic in the v0.9.1 draft is effectively: you cannot claim a higher level than the most restrictive set of MUSTs you satisfy. An agent that is missing a Purpose Declaration (I-4) cannot even be an Intern. An agent that only has identifiers and an owner but no capability manifest is stuck at Intern. This is deliberate — it forces operators to write down what an agent does before trusting it with bigger jobs.

Implementing ATF Conformance in air-trust v0.4.0

Here is the minimal code path for an Intern-level agent in the new air_trust release.

from air_trust import AgentIdentity
from air_trust.atf import conformance_statement, level_compliant

identity = AgentIdentity(
    agent_name="customer-search",
    owner="jason@airblackbox.ai",
    agent_version="1.0.0",
    org="AIR Blackbox",
    purpose="Answer customer questions from product documentation",
    capabilities=["search:docs", "llm:respond"],
    atf_level="intern",
)

print(conformance_statement(identity))
print("Intern compliant:", level_compliant(identity, "intern"))

Running that prints a full auditor-ready report and a pass/fail summary. The URN is auto-generated from org + name + version. The SHA-256 credential fingerprint is computed in __post_init__. You do not have to think about I-1, I-2, or I-3 at all — they are derived for you. You only have to write down I-4 and I-5.

Stricter Levels Are the Same Function, Different Argument

Promoting an agent to a higher level does not require new APIs. You change the atf_level field and re-run the conformance check.

identity.atf_level = "principal"

if not level_compliant(identity, "principal"):
    from air_trust.atf import gaps
    for req_id, reason in gaps(identity, "principal"):
        print(f"  {req_id}: {reason}")

The gaps() helper is the important one. It returns a list of tuples like ("I-5", "Capability Manifest missing") so you know exactly what to fix before promotion. This is how you wire ATF checks into a CI pipeline: gate a deployment on gaps(identity, target_level) == []. If it fails, the log tells developers exactly which core element to add.

The CLI

For operations teams who do not want to write Python, air-trust v0.4.0 ships a new subcommand. It accepts either explicit flags or a JSON config file and emits either a human-readable statement or JSON.

python -m air_trust atf \
    --name customer-search \
    --owner jason@airblackbox.ai \
    --org "AIR Blackbox" \
    --purpose "Answer customer questions from product docs" \
    --capabilities "search:docs,llm:respond" \
    --level intern

Sample output (trimmed):

CSA Agentic Trust Framework (ATF) Conformance Statement
============================================================
Agent:        customer-search
URN:          urn:agent:air-blackbox:customer-search:0.0.0
Target level: intern
Actual level: principal

  I-1  Unique Identifier      [MUST  ]  PASS
  I-2  Credential Binding     [SHOULD]  PASS
  I-3  Ownership Chain        [MUST  ]  PASS
  I-4  Purpose Declaration    [MUST  ]  PASS
  I-5  Capability Manifest    [SHOULD]  PASS

All MUST requirements for 'intern' level are satisfied.

Pipe it through --format json to feed the result into a compliance dashboard or a Technical Documentation bundle. The exit code is zero on a pass and one on a fail, so the same command works as a CI gate.

ATF and the EU AI Act Layer Together

This is the question I got from the first developer who saw the release: do I have to choose between CSA ATF and the EU AI Act? The short answer is no. They solve different problems and are explicitly designed to compose.

The EU AI Act tells you what your system must do: run risk management (Article 9), govern data (Article 10), keep technical documentation (Article 11), log decisions (Article 12), provide transparency (Article 13), enable human oversight (Article 14), and stay robust (Article 15). The ATF tells you how each individual agent inside that system should identify itself and earn progressively more trust. An EU AI Act Article 14 audit trail where every entry carries an ATF-conformant agent identity is strictly stronger than either standard alone, and satisfies both at once.

In air-trust v0.4.0, the same AgentIdentity object that feeds the HMAC-SHA256 audit chain also carries the ATF fields. One object, two regimes. If you already had the Article 14 wiring in place from an earlier version, you get ATF conformance almost for free — just add purpose and capabilities to the identity you were already building.

External Identity Providers

The framework explicitly allows external identity binding — a local URN plus a pointer to an external registry that can attest to the agent. air-trust v0.4.0 exposes this as the external_id field on AgentIdentity. It can hold any string the registry uses as a handle.

identity = AgentIdentity(
    agent_name="research-bot",
    owner="jason@airblackbox.ai",
    org="AIR Blackbox",
    purpose="Summarize academic papers",
    capabilities=["search:arxiv", "llm:summarize"],
    external_id="research-bot@agentlair.dev",  # external registry handle
    atf_level="junior",
)

The design is intentionally provider-agnostic. AgentLair-style handles work, did:web: URIs work, and so do custom HTTP registries. A provider adapter module is on the roadmap, but the core conformance check does not care where the external ID resolves — it only cares that one is declared.

Why This Is Worth Implementing Now

ATF v0.9.1 is still a public review draft, which is exactly why this is the right time to implement it. Three reasons:

  • The core elements are stable. I-1 through I-5 have been present since the earliest drafts. The review process is unlikely to change what a unique identifier or an ownership chain looks like.
  • Conformance claims mature with the framework. A library that implements the draft today will have running code the day v1.0 lands. Libraries that wait until v1.0 will ship a quarter late.
  • Enterprise procurement teams are already asking. I had three different buyers reference ATF maturity levels in January alone. Having a conformance statement you can attach to an Article 11 technical documentation bundle shortens the sales cycle.

None of this requires a cloud service or a subscription. The entire conformance module is local, deterministic, and open source under the same Apache 2.0 license as the rest of air-trust.

What Was Not Implemented (Yet)

Honest about limitations up front: v0.4.0 implements the Identity core element only. The broader ATF draft also covers Agent Actions, Agent Tools, Agent Governance, and the promotion gate machinery. Those are on the roadmap for v0.5.0 and v0.6.0. If you need them today, open an issue on the repo and I will prioritize whichever piece is blocking you. The Identity element is the right place to start because every other element of the framework assumes a stable agent identity exists first.

FAQ

What is the CSA Agentic Trust Framework?

The CSA Agentic Trust Framework (ATF) is a Cloud Security Alliance specification that defines how AI agents should prove identity, declare purpose, and earn progressively more trust through a four-stage maturity model. The v0.9.1 public review draft focuses on five Identity Core Elements (I-1 through I-5) that every autonomous agent should satisfy before it takes actions on behalf of a user or organization. It is not a regulation — it is a framework that plugs into existing regulatory regimes like the EU AI Act and ISO 42001.

How does CSA ATF relate to the EU AI Act?

The EU AI Act tells you what your AI system must do (risk management, audit trails, human oversight, transparency). The ATF tells you how each individual agent inside that system should identify itself and earn trust. They layer. An EU AI Act Article 14 audit trail with ATF-conformant agent identities is strictly stronger than either standard alone and satisfies both regimes at once. In air-trust v0.4.0 the same AgentIdentity object serves both purposes.

What are the five ATF Identity Core Elements?

I-1 Unique Identifier (a persistent URN for the agent), I-2 Credential Binding (a cryptographic fingerprint tying the agent to its code and owner), I-3 Ownership Chain (a human or organization who is accountable), I-4 Purpose Declaration (what the agent is for), and I-5 Capability Manifest (what the agent is allowed to do). At Intern level I-1, I-3 and I-4 are MUST and I-2 and I-5 are SHOULD. Senior and Principal levels make all five MUST.

Do I need to pick a side between ATF and EU AI Act compliance?

No. The two frameworks solve different problems and are designed to compose. air-trust v0.4.0 emits the same audit events that feed EU AI Act Article 12 logging and adds an atf.conformance() check for each agent identity. One install, both regimes. You do not need a second library, a second service, or a second data model.

How do I check ATF conformance in Python?

Install air-trust v0.4.0, build an AgentIdentity with purpose and capabilities fields, then call air_trust.atf.conformance(identity) for the per-requirement result, air_trust.atf.level_compliant(identity, "intern") for a level check, or air_trust.atf.conformance_statement(identity) for a human-readable auditor report. A CLI (python -m air_trust atf) is also included for non-Python workflows.

Is this an official CSA implementation?

No. air-trust is an independent open-source implementation of the public review draft. It is not endorsed by the Cloud Security Alliance. We track the spec closely and will update conformance semantics as the draft moves toward v1.0. If you are using air-trust for a regulated audit, pair the conformance statement with a direct reading of the current ATF draft — the library output is a starting point, not a substitute for reading the spec.
